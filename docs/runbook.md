## Deploy

- **Normal path: merge to `main`.** The service has `autoDeployTrigger: commit`, so every push to
  `main` builds the Dockerfile and deploys. The Blueprint has auto-sync on, so a `render.yaml`
  change on `main` is applied too.
- Each deploy runs `preDeployCommand: node packages/db/dist/migrate.js` before the new instance
  takes traffic. It applies pending `drizzle/` migrations and logs migration names only. If it
  fails, the deploy fails and the previous deploy keeps serving.
- Render then waits for `GET /readyz` to answer 200 (Postgres `select 1` within 2 s and pg-boss
  started) before it switches traffic.
- **First setup or re-sync:** `scripts/setup.sh` (idempotent). It checks `render whoami` and
  `gh auth status`, validates `render.yaml` (`render blueprints validate`), and requires
  `render.yaml` on `main`. The first run creates the Blueprint from `main`
  (`render ea blueprints create`) and approves its first sync. Later runs plan a sync
  (`render ea blueprints plan`) and approve only real changes. Then it prints the IDs and the URL.
  On a missing GitHub connection or payment method it exits non-zero and names the owner step.
- **Manual redeploy of main** (for example, after the owner sets an env value):
  `render deploys create <srv-id> --wait --confirm`.
- **State without changing anything:** `scripts/setup.sh --status` prints one JSON object:
  `url`, `region`, `plan`, `postgres_version`, `postgres_region`, `last_deploy {id,status,commit}`.
- **Owner-set values** (`sync: false` in `render.yaml`, P-22): `APP_BASE_URL`,
  `BOOTSTRAP_ADMIN_EMAIL`, `ANTHROPIC_API_KEY`, `LLM_PROVIDER`, `LLM_MODEL`,
  `LLM_DAILY_SPEND_CAP_USD`, `LLM_BATCH_TOKEN_CAP`. Set them in Render dashboard → service `4x35` →
  Environment → Edit → Save. Saving triggers a deploy. Until they are set they are empty, and the
  server treats an empty value as unset: it boots without them, and the LLM stays off (opt-in).
  Never copy a value from a local `.env`.
- **Create the first owner (once, after P-22 sets `BOOTSTRAP_ADMIN_EMAIL` and `APP_BASE_URL`):**
  open a shell on the running instance, either dashboard → service `4x35` → **Shell** or
  `render ssh srv-dc59d1s9v7es739n2qfg`, then run, from `/app`:
  `node apps/server/scripts/bootstrap-admin.ts`. It prints the one-time owner invite URL (72 h) to
  that terminal only. A re-run prints that the invite is pending and creates nothing. The npm
  script `bootstrap:admin` (`tsc -b && …`) is for a source checkout; the image has no sources to
  build, so call `node` directly.
- `SESSION_SECRET` and `CSRF_SECRET` are generated by Render (`generateValue: true`, a base64
  256-bit value) on first sync and are kept on later syncs.

## Roll back to the previous deploy

Needs the owner's yes (not covered by standing approval 2).

1. Find the previous live deploy: `render deploys list <srv-id> -o json` (or dashboard → service
   `4x35` → Deploys).
2. Dashboard → service `4x35` → Deploys → that deploy → **Rollback** → **Rollback to this deploy**.
   Render redeploys that deploy's build artifact; no rebuild. The Hobby workspace keeps the last 5
   builds.
3. **A dashboard rollback turns auto-deploy off** for the service. Pushes to `main` stop
   deploying until it is turned back on: dashboard → service `4x35` → Settings → Auto-Deploy →
   On Commit. (The REST "roll back deploy" endpoint does not change auto-deploy.)
4. Check `curl -fsS <url>/healthz` (200, `status: "ok"`, `commit` = the rolled-back commit) and
   `<url>/readyz` (200).
5. Restore main: turn auto-deploy back on, then `render deploys create <srv-id> --wait --confirm`
   (deploys `main`'s HEAD). Check that `/healthz` reports `main`'s commit.

A rollback does not undo migrations. Migrations are forward-only, so a migration that breaks an
older build is fixed forward with a new migration on `main`.

## Restore from backup (RPO 24 h, RTO 4 h, R4)

Backups on the chosen plan (Render docs, read 28 Nov 2026, https://render.com/docs/postgresql-backups):

- **Point-in-time recovery (PITR):** paid Postgres instances are backed up continuously. The
  recovery window is the **past 3 days** on a Hobby workspace (7 days on Pro or higher). This
  beats the 24 h RPO.
- **Logical exports:** dashboard → database `4x35-db` → Recovery → **Create export** (one at a
  time). Render keeps each export 7 days. Download it as `.dir.tar.gz` and restore with
  `pg_restore`.

PITR steps:

1. Dashboard → database `4x35-db` → **Recovery** → Point-in-Time Recovery → **Restore database**.
2. Name the new instance (for example `4x35-db-restore-<date>`), pick the time (not within 10
   minutes of now), choose Copy Existing Settings = Yes, then **Start Recovery**. Render creates a
   **new** database instance: Recovery In Progress → Creating → Available.
3. Check it (Info → PSQL Command, from an allowed IP; `4x35-db` is private-network only,
   `ipAllowList: []`, so connect from the service shell `render ssh <srv-id>` instead).
4. Point the service at it: set `fromDatabase.name` in `render.yaml` to the new instance and merge
   (owner approval: this is a production write), or set `DATABASE_URL` in the dashboard. The
   resulting deploy runs the migrations, which are a no-op on restored data.
5. Once the service is healthy on the restored database, suspend the old instance. Delete it only
   with the owner's OK. Record the restore on the issue that caused it.

## Rotate `SESSION_SECRET` (and `CSRF_SECRET`)

Rotating `SESSION_SECRET` signs everyone out, because stored session hashes are keyed by it.
Rotating `CSRF_SECRET` invalidates in-flight forms.

1. Generate a value locally without printing it to a shared log: `openssl rand -base64 32`.
2. Dashboard → service `4x35` → Environment → `SESSION_SECRET` → Edit → paste → Save changes
   (triggers a deploy). Both keys must be at least 32 characters and must differ.
3. Check `/readyz` is 200 after the deploy, then sign in again.

The Blueprint never overwrites an existing `generateValue` key, so a later sync keeps the
rotated value.

## Health checks and logs

- `GET /healthz`: liveness, no database. 200 `{"status":"ok","version","commit"}`. `commit` is
  the deployed git SHA (Render's `RENDER_GIT_COMMIT` when the image has none baked in). The
  Dockerfile `HEALTHCHECK` and the CI smoke use it.
- `GET /readyz`: readiness, and Render's `healthCheckPath`. 200 when Postgres answers
  `select 1` within 2 s and pg-boss is started, 503 otherwise (M1-05).
- **Logs:** pino JSON lines on stdout. Allow-listed fields only, never content or env values.
  Dashboard → service `4x35` → Logs, or the CLI:
  `render logs --resources <srv-id> --tail -o text` (`--level error`, `--text <s>`,
  `--start/--end` to filter). The Hobby workspace keeps logs 7 days.
- Pre-deploy (migration) output appears in the deploy's log: dashboard → Deploys → the deploy.
