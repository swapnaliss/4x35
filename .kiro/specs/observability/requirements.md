# Requirements Document

## Introduction

Ticket M1-05 (ADR 0015, architecture §9) gives 4x35 its observability baseline. The server writes pino JSON logs that carry request and job correlation IDs and no file content, because addresses are personal data (R8). Each job attempt writes one `job_timings` row. A dead-letter listing shows failed jobs without their payload. `GET /healthz` and `GET /readyz` serve the Render health check. The SLOs (health report p95 ≤ 30 s, job failure rate < 1%) can only be measured with these in place; M3-08 reads `job_timings`.

Out of scope: an owner-only dead-letter HTTP route (M1-08); tracing, metrics endpoints and APM (ADR 0015 rejects them for now); the daily synthetic run of the core flow on a sandbox workspace (M3-09).

Decisions taken before this spec (not reopened): the `job_timings` table already exists (`packages/db/src/schema/ops.ts`) with columns `job_id`, `kind`, `batch_id`, `chunk`, `ms` (≥ 0) and `outcome` (`completed`, `failed` or `dead_letter`); the job wrapper sits around `defineJob` from M1-04; the originating request ID travels in the job payload metadata.

## Glossary

- **Observability_Baseline**: the M1-05 deliverables as a whole: Logger, Request_Id_Middleware, Job_Wrapper, Health_Endpoints, Dead_Letter_Lister and Render_Config.
- **Logger**: the pino 10.4.0 instance in `apps/server/src/obs/logger.ts`.
- **Log_Serializer**: the allow-list of fields the Logger writes for a request or a job.
- **Redactor**: the redaction step of the Logger, applied to every logged object.
- **Request_Id_Middleware**: the request middleware in `apps/server/src/obs/request-id.ts`.
- **Request_Id**: the correlation ID of one HTTP request, carried by the `X-Request-Id` header.
- **Job_Wrapper**: the wrapper around `defineJob` in `apps/server/src/obs/job-wrapper.ts`.
- **Job_Timings**: the `job_timings` table, one row per job attempt.
- **Health_Endpoints**: the routes `GET /healthz` and `GET /readyz` in `apps/server/src/obs/health.ts`.
- **Dead_Letter_Lister**: `listDeadLetters(tx, {limit})` in `apps/server/src/obs/dead-letters.ts`.
- **Dead_Letter_Script**: the command `npm run jobs:dead-letters -w apps/server`, which runs `apps/server/scripts/dead-letters.ts`.
- **Render_Config**: `render.yaml`.
- **AuthZ_Matrix**: the route authorization matrix from M1-03.
- **MODE**: the process mode `web`, `worker` or `all`.
- **Marker_String**: a random string, generated by fast-check, placed in a request body or job payload so a test can detect it in a log line.

## Requirements

### Requirement 1: Logger configuration

**User Story:** As an operator, I want structured JSON logs at a configurable level, so that logs can be filtered and parsed.

#### Acceptance Criteria

1. THE Logger SHALL write log lines at the level set by `LOG_LEVEL`.
2. WHILE the environment is production, THE Logger SHALL write JSON log lines.

### Requirement 2: Allow-listed log fields

**User Story:** As a data-protection owner, I want only listed fields in logs, so that personal data never reaches them.

#### Acceptance Criteria

1. WHEN the Logger records a request, THE Log_Serializer SHALL write only the method, route pattern, status, duration, request ID, user ID, workspace ID and the `user-agent` header (the one header 2.4 allows).
2. WHEN the Logger records a job, THE Log_Serializer SHALL write only the kind, job ID, batch ID, chunk, attempt, outcome and ms.
3. THE Log_Serializer SHALL write no request body, no query string, no cookie and no file name.
4. THE Log_Serializer SHALL write no request header other than `user-agent`.
5. THE Redactor SHALL redact the paths `password`, `token`, `*.original*`, `*.lines*` and `*.name`.

### Requirement 3: No content in logs

**User Story:** As a data-protection owner, I want proof that logs carry no file content, so that addresses stay out of log storage.

#### Acceptance Criteria

1. FOR ALL requests whose bodies and jobs whose payloads contain Marker_Strings, including CJK and Devanagari characters, THE Logger SHALL write no log line that contains any Marker_String (`P-logs-carry-no-content`).

### Requirement 4: Request correlation ID

**User Story:** As an operator, I want one ID per request in every log line and in the response, so that I can follow a request through the logs.

#### Acceptance Criteria

1. WHEN a request carries an `X-Request-Id` header that matches `^[A-Za-z0-9-]{8,64}$`, THE Request_Id_Middleware SHALL use that value as the Request_Id.
2. IF a request carries no `X-Request-Id` header, THEN THE Request_Id_Middleware SHALL generate a Request_Id.
3. IF a request carries an `X-Request-Id` header that does not match `^[A-Za-z0-9-]{8,64}$`, THEN THE Request_Id_Middleware SHALL generate a Request_Id and discard the incoming value.
4. WHEN a request is handled, THE Request_Id_Middleware SHALL set the Request_Id in the `X-Request-Id` response header.
5. WHEN a request is handled, THE Request_Id_Middleware SHALL bind a child Logger carrying the Request_Id to that request.
6. FOR ALL log lines written for a request, THE Logger SHALL write a `requestId` equal to the `X-Request-Id` response header of that request.

### Requirement 5: Job correlation and timings

**User Story:** As an operator, I want job logs tied to the originating request and one timing row per attempt, so that the job failure rate and durations can be measured.

#### Acceptance Criteria

1. WHEN a job runs, THE Job_Wrapper SHALL bind a child Logger carrying the job ID and the originating Request_Id from the job payload metadata.
2. WHEN a request enqueues a job, THE Job_Wrapper SHALL log the Request_Id of that request on each line the job writes.
3. WHEN a job attempt ends, THE Job_Wrapper SHALL insert one Job_Timings row with `job_id`, `kind`, `batch_id`, `chunk`, `ms` and `outcome`.
4. WHEN a job succeeds on its first attempt, THE Job_Wrapper SHALL hold 1 Job_Timings row for that job with outcome `completed`.
5. WHEN a job fails 3 times and is then dead-lettered, THE Job_Wrapper SHALL hold 4 Job_Timings rows for that job with the outcomes recorded for each attempt.

### Requirement 6: Health endpoints

**User Story:** As an operator, I want a liveness and a readiness endpoint, so that Render can tell a running process from a ready one.

#### Acceptance Criteria

1. WHEN `GET /healthz` is called, THE Health_Endpoints SHALL return 200 without querying the database.
2. WHEN `GET /readyz` is called and `select 1` on the database completes within 2 seconds, THE Health_Endpoints SHALL return 200.
3. WHERE MODE is `worker` or `all`, WHEN `GET /readyz` is called and pg-boss has not started, THE Health_Endpoints SHALL return 503.
4. IF `select 1` does not complete within 2 seconds or fails, THEN THE Health_Endpoints SHALL return 503.
5. IF Postgres is stopped, THEN THE Health_Endpoints SHALL return 503 for `GET /readyz` within 3 seconds and 200 for `GET /healthz`.
6. THE Health_Endpoints SHALL be public, and the AuthZ_Matrix SHALL register `GET /healthz` and `GET /readyz` as `public` once M1-03 has landed.

### Requirement 7: Dead-letter listing

**User Story:** As an operator, I want to list dead-lettered jobs without seeing payloads, so that I can find permanent failures without exposing personal data.

#### Acceptance Criteria

1. WHEN `listDeadLetters` is called with a transaction and a limit, THE Dead_Letter_Lister SHALL return at most `limit` dead-lettered jobs, each with kind, job ID, batch ID, attempts and error class.
2. THE Dead_Letter_Lister SHALL return no job payload.
3. WHEN the Dead_Letter_Script runs, THE Dead_Letter_Script SHALL print the kind, job ID, batch ID, attempts and error class of each dead-lettered job and no payload.
4. WHEN a job has failed 3 times and been dead-lettered, THE Dead_Letter_Script SHALL list that job.

### Requirement 8: Render health check

**User Story:** As an operator, I want Render to check readiness, so that an instance without a database is not treated as healthy.

#### Acceptance Criteria

1. THE Render_Config SHALL set `healthCheckPath: /readyz`.

### Requirement 9: Spec and usage record

**User Story:** As a reviewer, I want the spec and its Kiro usage recorded, so that the ticket's deliverables are traceable.

#### Acceptance Criteria

1. THE Observability_Baseline SHALL record this spec at `.kiro/specs/observability/` with `requirements.md`, `design.md` and `tasks.md`.
2. THE Observability_Baseline SHALL record an entry for M1-05 in `docs/kiro-usage.md`.
